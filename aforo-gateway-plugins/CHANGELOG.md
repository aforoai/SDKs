# Aforo Gateway Plugins — Changelog

This monorepo ships five gateway metering plugins (Kong, Apigee, AWS Lambda, Azure APIM, MuleSoft). Each plugin carries its own version (see its directory); as of 2.2.0 all five are aligned.

## v2.2.0 — 2026-10-02

All five plugins are 2.2.0. This release merges two lines that had diverged since 2026-06-29: the public release 2.1.0 (`aforoai/SDKs`, work by Gowtham and Eswar: verified identity, metric mappings, product type, Retry-After, the Kong RS256 verifier, per-plugin docs and the Kong demo) and this repository's line (execution-status table and overrides, default exclusions, `X-API-Key`, frozen idempotency keys, Kong gRPC / GraphQL / WebSocket and `customer_id_jwt_claim`, the Apigee X fixes and bounded delay, APIM-valid Azure fragments, the MuleSoft policy package). The entries under "Before the merge" below are this repository's changes since v2.0.4 and are part of 2.2.0.

**Versions.** Each plugin records 2.2.0 in its own place: Kong rockspec + `handler.lua` `VERSION` (the internal handler numbering 1.3.0–1.4.4 used below is retired), `aws-lambda/package.json`, `apigee/VERSION`, `azure-apim/VERSION`, `mulesoft/VERSION` + `mulesoft/aforo-metering/pom.xml` (the package was 1.0.0). `aws-cloudformation` and `azure-arm-templates` stay 1.0.0. Tags on the public repository: `kong-v2.2.0`, `apigee-v2.2.0`, `aws-lambda-v2.2.0`, `azure-apim-v2.2.0`, `mulesoft-v2.2.0`.

**Config compatibility.** Every setting either line read is still read. Renamed-in-one-line settings are aliases: MuleSoft `product_type` / `default_metric` / `quantity_source` / `include_metadata` (canonical: hyphenated); Azure 2.1.0 Named Values are bridged to context variables by `aforo-context`, except the compound / preflight / margin-guard ones, which need the `set-variable` lines in `azure-apim/CHANGELOG.md`. AWS SAM parameters `AforoTenantId` and `CustomerIdSource`, removed in 2.1.0, are accepted again.

**What changes for an existing install** (details in each plugin's `CHANGELOG.md`):
- No verified customer, no event. An API key value, a subscription key or a client IP is never a `customerId`. AWS stages metered through an API Gateway API key alone send nothing until the access log carries `$context.authorizer.customerId` or an IAM caller.
- The default metric is `api_calls`, not `{method} {path}` (Azure without `aforo-context` keeps `METHOD path` until `aforo-default-metric` is set). A configured pattern still applies.
- 2.1.0 installs gain the default exclusions (401/403/429, health paths) and the execution-status table.
- Kong: `jwt_allow_unverified_signature` grants access but no longer supplies identity; the JWT verifier requires `alg: RS256`, a numeric `exp`, and checks `nbf`.
- CORS preflights and quantity ≤ 0 are not metered. `X-Tenant-Id` is no longer sent to the ingestor except by Kong.

**Not run on a real gateway.** Unit and structural suites only: Kong (busted against a PDK mock), AWS (local capture server), Apigee, Azure (mock context), MuleSoft (structure + `mvn package`). `demo/` needs Docker and a running ingestor.

### Before the merge (this repository, 2026-09-30 → 2026-10-01)

- **Apigee: an ingest outage can no longer add about 15 seconds to an API call.** The shared flow runs before the client gets its response (`PostProxyFlowHook`), and it made three attempts with a 5 s connect timeout and a 10 s response timeout each. Now: 1 s to connect, 2 s for the response, and one retry instead of two. The retry runs only when the first attempt failed to connect or got a 5xx, and failed within 1.2 s; a 4xx is never re-sent (a 429 used to be), and a response timeout is not retried. Worst case: about 2 s when ingest is unreachable, about 3 s when it accepts the connection and never answers, about 4 s at the limit. New KVM entry `max_retries` (`0` or `1`, default `1`, clamped). The two timeouts are fixed in the policies: Apigee accepts only literals for ServiceCallout timeouts, so they cannot be read from the KVM. `AforoMeteringReadConfig` and `AforoMeteringBuildEvent` now have `continueOnError="true"` as well, and the send does not run without a built payload and an endpoint, so a missing KVM cannot fail the API call. A dropped event (now including one the ingestor refused with a 4xx) prints `USAGE EVENT DROPPED` and sets `aforo.meteringDeliveryFailed` / `Reason` / `LastStatus` / `Attempts`. New policy `AforoMeteringRetryGate` and script `aforo-metering-retry-gate.js`; `AforoMeteringSendEventRetry2` is deleted. The payload, idempotency key (Rule #21), exclusions and status mapping are unchanged. Not run on an Apigee organization. Tests 296/296 (was 197). The other four plugins send off the request path (Kong: batched in a timer; AWS: Lambda on CloudWatch logs; Azure: `send-one-way-request`; MuleSoft: `<async>` scope) and are unchanged.
- **Kong: `customer_id_jwt_claim`, and no event without an identity (handler 1.4.4).** New optional config `customer_id_jwt_claim`: take `customerId` from a claim of the JWT that Kong's bundled `jwt` plugin verified on the same route or service. The claim is read from `kong.ctx.shared.authenticated_jwt_token`, which that plugin sets only after the signature check; a token that is merely present in the `Authorization` header is never read, and no request header is. In this mode the Kong consumer is not used: on a `jwt` route the consumer is the token issuer, shared by every caller. New `customer_id_jwt_exclude_claims` (array): a verified token carrying any of these claims is not metered, e.g. staff impersonation. The claim must be a string of 1 to 64 characters. **Behaviour change:** a request with no resolvable customer identity now produces no event on every path (standard, MCP, gRPC, GraphQL, WebSocket). It used to send `customerId: null`, which the ingestor rejects, so no accepted event is lost. Existing configs are unaffected otherwise: without the new option the Aforo-JWT claim and the consumer are used as before. Idempotency keys untouched (Rule #21); the 401/403/429 and health-path exclusions run before identity is resolved. Specs 92/92 (was 78).
- **All five plugins send the API key as `X-API-Key` (Kong handler 1.4.3); default endpoint is `https://api.aforo.ai/v1/ingest/batch`.** One standard for sending usage to Aforo, the same as the SDKs. The plugins sent `Authorization: Bearer <key>`. The ingestor accepts both forms for an `sk_live_` / `sk_test_` key, so nothing changes for a deployed plugin and the configured key is read from the same place (Kong `api_key`, AWS `AFORO_API_KEY`, Apigee KVM `api_key`, Azure Named Value `aforo-api-key`, MuleSoft `aforo-api-key`). Changed senders: Kong `handler.lua`; AWS `index.js`, `compound-metering.js`, `preflight-quota.js`; Apigee `AforoMeteringSendEvent*.xml`; Azure `outbound-policy.xml` and the compound and pre-flight fragments; MuleSoft `template.xml`. A configured endpoint is used as-is. The AWS SAM default was `https://ingest.aforo.ai/v1/ingest/batch`, a host that answers a POST with a 301; it is now `https://api.aforo.ai/v1/ingest/batch`. Idempotency keys untouched (Rule #21).
- **MuleSoft: the metering policy is now an installable Mule 4 package (`mulesoft/aforo-metering/`, policy version 1.0.0).** `pom.xml` (packaging `mule-policy`, mule-maven-plugin 4.10.1), `mule-artifact.json`, the policy definition `aforo-metering.yaml` and `src/main/mule/template.xml`. `mvn clean package` builds `aforo-metering-1.0.0-mule-policy.jar` from public MuleSoft repositories; `mvn clean deploy -Danypoint.org.id=<org id>` publishes the jar and the definition to your Exchange. `mule-policy.yaml` and the root `template.xml` are gone: the metering script now lives only in the packaged template. The script itself is unchanged (status mapping, exclusions, MCP and AGENTIC_API detection, idempotency keys, `occurredAt`, 2-retry send). What changed around it, because the old files could not run on Mule 4:
  - The template is a real `http-policy:proxy` / `source` / `execute-next` policy. Policy properties are rendered with Handlebars; the old `${...}` placeholders would have been resolved against the API's own properties. The router is `<choice>`; `<choose>` is not a Mule element.
  - **Identity** comes from `authentication.properties.claims`, set by MuleSoft's JWT Validation policy. The old `vars.aforo.*` contract relied on another policy's variables, which Mule 4 does not share between policies. New optional properties `customer-id-claim` (default `customer_id`, then `sub`) and `tenant-id-claim` (default: stamp the configured `aforo-tenant-id`).
  - **Request id**: a UUID minted once when the request arrives and held for the life of the request, so every delivery attempt carries the same key (Rule #21). It is not read from a header a caller can set.
  - `try(...)` in the script now resolves: the template defines it over `dw::Runtime::try`, returning the value or null. Without that the script did not compile and MCP detection could never match.
  - Request capture and the send swallow their own errors; the API call is never failed by the policy.
  - Not covered, and stated in the README: unhandled flow errors, Flex Gateway, Mule 3, client-ID-only APIs, `occurredAt` on a runtime whose zone is not UTC.

APIM substitutes `{{...}}` in the policy text and refuses to save a policy that references a missing Named Value; whether it skips comments was not verified against a live instance, so the example is reworded and can no longer matter. An excluded request produces no event and no outbound call, on the standard, MCP and AGENTIC_API paths. Defaults: status `401,403,429`; paths `/health,/ready,/metrics` (equal-or-prefix). A configured list replaces the default; `none` excludes nothing; junk entries are ignored and never raise. **Azure**: context variables `aforo-exclude-status-codes` and `aforo-exclude-paths`, set before the `include-fragment` (like `aforo-status-outcomes`); `outbound-policy.xml` computes `aforo-skip` once and both sends sit behind it. - **All five plugins: new `executionStatus` default table, and per-code overrides (Kong handler 1.4.0).** Only 400 and 422 are now `VALIDATION_FAILED`. 401, 403 and 429 are `BLOCKED`, and 404 plus every other 4xx is `ERROR`. Previously every non-408 4xx was `VALIDATION_FAILED`, so under the usual weight of 0 an unauthenticated, forbidden, missing-route or rate-limited call billed as free. 2xx/3xx → `SUCCESS`, 408/504 → `TIMEOUT` and 499 → `CANCELLED` are unchanged. Each plugin accepts exact-code overrides (Kong `status_outcomes` map; AWS `STATUS_OUTCOMES`; Apigee KVM `status_outcomes`; Azure context variable `aforo-status-outcomes`; MuleSoft `status-outcomes`), validated against the 11 canonical statuses, with invalid entries ignored. See README "Execution status mapping", which also records why the table changed.
- **Kong: gRPC failures no longer bill as `SUCCESS`.** gRPC answers most failures with HTTP 200 and puts the result in the `grpc-status` trailer. The handler now reads it (response header, then `$upstream_trailer_grpc_status`, then `$sent_trailer_grpc_status`) and maps it through an equivalent HTTP status, so the same table and overrides apply: 16 UNAUTHENTICATED, 7 PERMISSION_DENIED and 8 RESOURCE_EXHAUSTED are `BLOCKED`, and 4 DEADLINE_EXCEEDED is `TIMEOUT`. Missing `grpc-status` falls back to the HTTP status. `grpcStatusCode` now also reads the trailer, not just the header. The other four gateways don't meter gRPC.
- **AWS Lambda: the statuses it doesn't meter are now configurable.** 401/403/429 were skipped by a list written into the code; `EXCLUDE_STATUS_CODES` (SAM `ExcludeStatusCodes`, same default) now controls it, matching Kong's `exclude_status_codes`.

Azure APIM has no harness; the fragment is well-formed once expression bodies are masked, the same as before. Idempotency keys and compound `correlationId` derivation are untouched (Rule #21).

- **Kong: gRPC, GraphQL and WebSocket detection ported in, with fixed idempotency keys (handler 1.3.0).** Until now these three paths existed only in the `aforo-nextgen-docker` deploy copy, which had drifted from this repo in both directions. There the keys ended in `tostring(ngx.now())` and fell back to `kong.tools.uuid()`. The clock suffix made any re-evaluation mint a new key, so a retry would bill twice (Rule #21). `kong.tools` is nil on Kong 3.x, so a request with no request id crashed the log phase and emitted nothing. Keys are now `grpc:<tenant>:<request-id>:<Service>/<Method>`, `gql:<tenant>:<request-id>:<operation>` and `ws:<tenant>:<Sec-WebSocket-Key>`. With no request id, the fallback is one `resty.jit-uuid` value that is stored with the buffered event and sent unchanged on every flush retry. New config (all off by default): `grpc_enabled`/`grpc_product_id`/`grpc_path_prefix`, `graphql_enabled`/`graphql_product_id`/`graphql_path_pattern`, `websocket_enabled`/`websocket_product_id`, plus `product_type` (default `API`). Plain HTTP events now carry `productType`; the ingestor's prod profile rejects events without one. gRPC and GraphQL events also carry `executionStatus`. This file is now the single source: the docker repo ships byte-identical copies, checked by its `kong/scripts/check-plugin-sync.sh`. Specs: 58/58, including source locks that fail on any clock in a key or any `kong.tools` call.
- **All five plugins: `executionStatus` on every standard API and AGENTIC_API event**, derived from the upstream HTTP status, so `OUTCOME_BASED` pricing works for plain API traffic and not only MCP tool calls. Shared table: 2xx/3xx → `SUCCESS`, 408/504 → `TIMEOUT`, 499 → `CANCELLED`, other 4xx → `VALIDATION_FAILED`, other 5xx → `ERROR`; undeterminable status → field omitted (never `null`/`""`). See README "Execution status mapping". Other pricing models ignore the field, so this is a no-op for non-outcome plans.
- **MCP tool calls now follow the same table.** 2xx stays `SUCCESS`; previously every non-2xx was `ERROR`, now a 504 is `TIMEOUT`, a 4xx is `VALIDATION_FAILED`, and a 3xx is `SUCCESS`. Apigee also maps a JSON-RPC `error` object inside a 2xx MCP response to `ERROR` (it reads the already-buffered `response.content`); Kong, AWS Lambda, Azure APIM, and MuleSoft don't have the response body and classify on status alone.
- Kong change applied to both `kong/handler.lua` and the `aforo-nextgen-docker` deploy copy. Compound-metering paths unchanged (the compound request has no `executionStatus` field); correlationId derivation untouched.

## v2.0.3 — 2026-07-29 (BROKEN — DO NOT USE)

The rockspec that shipped on this tag has `version = "2.0.2-1"` and `source.tag = "v2.0.2"` internally, so `luarocks install` against v2.0.3 checks out v2.0.2 (pre-crash-fix) code. Use v2.0.4 instead. Left in place for immutable-tag discipline; the GitHub Release page carries the same warning.

Delivery-guarantee hardening (A+ prompts 3 + 4). Prompt 3 covered the two plugins with already-stable idempotency keys (AWS Lambda, Kong). Prompt 4 covers the three fire-once plugins (Apigee, Azure APIM, MuleSoft) under the iron rule **freeze the key first, add retry second**: each plugin's idempotency key was made stable across delivery attempts (clock components removed) BEFORE any retry landed, so a redelivery dedups at the ingestor instead of double-billing. All changes are additive and backward-compatible; retries never touch the customer's API response path.

**Compound-key freeze follow-up (2026-07-05).** Prompts 3-4 froze the STANDARD and MCP keys, but every gateway also has a separate compound-metering path whose `correlationId` was still minted randomly per evaluation. That was harmless while the gateways were fire-once; the retry/redelivery those prompts added turned it into a live double-bill vector — the server (`CompoundEventDecomposer`) derives EVERY per-metric dedup key from the compound `correlationId` (`correlationId:metricName[:dimensionKey]:index`), so a redelivered compound event with a fresh id decomposes to entirely new keys and bills every metric twice. All five compound paths are now frozen to each gateway's stable per-request identity — the same identity its standard key was frozen to — hashed into a v3-style UUID where the identity isn't UUID-shaped (the server types `correlationId` as `UUID`; a raw non-UUID value 400s and silently drops the event). Freeze-only: no retry, wire-format, or decomposition changes.

- **AWS Lambda (compound, LIVE vector): `buildCompoundEvent` minted `uuidv4()` per invocation** — under prompt 3's throw→CloudWatch-redelivery, a redelivered compound event double-billed every measurement. Now derived from the caller's log-data seed (`parsed.requestId || logEvent.id`, the prompt-3 standard-key identity; `metadata.requestId` fallback; warned random last resort) via md5 → v3-style UUID. Also fixes a broken-as-shipped `require('uuid')` — `uuid` was never in `package.json` dependencies, so the module failed at require time; now `node:crypto` only. +5 assertions in the test suite (43/43) prove the correlationId is byte-identical across two invocations of the same awslogs payload and derived with zero entropy.
- **Kong (compound, latent): `build_compound_event` minted `kong.tools.uuid()` per build.** Per-flush audit verdict: the module is standalone and unwired (rockspec-documented, not packaged; `handler.lua` never requires it), so the prompt-3 3-retry never touches it in-repo — but any customer wiring that rebuilds per attempt would double-bill. Now derived from `X-Request-Id` header (mirroring the handler's frozen standard-key preference) > `ngx.var.request_id`, via `ngx.md5` → v3-style UUID; rebuilds within a request are byte-identical by construction. Verified with a mocked-`kong`/`ngx` harness against node-computed reference UUIDs (6/6). No hand-synced docker copy exists for this module (docker ships only `handler.lua` + `schema.lua`).
- **Apigee (compound): `messageid || java.util.UUID.randomUUID()` had THREE defects** — (1) the random fallback was per-evaluation (the freeze target); (2) raw `messageid` is not UUID-shaped (`rrt-…`), so the ingestor's UUID-typed `correlationId` rejected it with a 400 and silently dropped the event; (3) `java.util.UUID` does not exist in Apigee's sandboxed Rhino — the fallback would have thrown. Now `messageid` > `x-request-id` header (the prompt-4 standard-key preference) hashed via an embedded pure-JS MD5 (public-domain Joseph Myers, verified byte-for-byte against `node:crypto` including block/padding edges) → v3-style UUID; UUID-shaped `Math.random` last resort. +18 unit tests (39/39). The file remains unreferenced by any bundle policy (same posture as `aforo-mcp-metering.js` — frozen anyway).
- **Azure APIM (compound, latent — retry deferred): `Guid.NewGuid()` per evaluation → `context.RequestId`** — the same stable per-request GUID the standard key was frozen to (`aforo-idempotency-key-base`). Already a Guid, so no hashing needed. Future-safe for the planned `log-to-eventhub` durable transport. Comment-plus-one-token diff; the fragment keeps the fleet's APIM-parser-validated (not xmllint-valid) posture.
- **MuleSoft (compound): the correlationId had NO in-repo source at all** — `compound-metering-policy.yaml` is a policy definition whose implementation lives in its comment spec, and that spec never mentioned `correlationId`, leaving implementers to mint their own (typically `uuid()` — per-evaluation). The spec now MANDATES deterministic derivation from Mule's stable per-event `correlationId` attribute (the `template.xml` standard-key identity, stable across `until-successful` retries) via `dw::Crypto` MD5 → v3-style UUID, with a copy-paste DataWeave snippet and an explicit ban on `uuid()`/`now()`/`randomBytes()`. YAML validated.

**Post-ship self-review (same day) — one created bug fixed, two discovered bugs fixed:**

- **Kong (created by the freeze, fixed before any release): empty `X-Request-Id` header derived a SHARED correlationId.** Lua treats `""` as truthy, so a client sending an empty `X-Request-Id` value made `get_header(...) or ngx.var.request_id` pick the empty string — every such request derived the SAME v3 UUID, and the ingestor silently deduped their real compound events as replays (revenue loss, undetectable because the shared id is a valid UUID; the JS gateways are immune since `''` is falsy in JS). Empty headers now normalize to nil and fall through the identity chain. Regression-locked by the NEW committed spec `kong/spec/compound_metering_spec.lua` (7 cases, incl. the empty-header lock, asserting node-verified reference UUIDs).
- **Kong (discovered, same Lua-truthiness family, both hand-synced copies): `handler.lua` read `X-Request-Id` raw at the key-construction site** — an empty header shadowed the `X-Kong-Request-Id` fallback and fed a blank/shared component into idempotency keys (the prefixed MCP — and in the deploy copy grpc/gql — keys could collide ACROSS requests → false dedup; the bare standard key degraded to blank → server-side auto-UUID, a dedup opt-out). Normalized `""`→nil in BOTH copies (this repo, VERSION → 1.2.1, and the leaner `aforo-nextgen-docker` deploy copy).
- **Azure APIM (discovered, pre-existing since the fragment was authored): operator-precedence bug dropped ENTIRE compound events.** `token != null && token.Type == Integer || token.Type == Float` parses as `(A && B) || C` — any configured extraction path missing from a response made `C` dereference the null token → `NullReferenceException` → the outer catch returned `"[]"` → the whole compound event was dropped, including measurements whose paths DID match. Since configs routinely list more paths than any single response contains (the default LLM set lists 3), this silently dropped most Azure compound events. Parenthesized; family-swept — the Kong/Lambda/Apigee extractors guard correctly.

### Fixed

- **Kong (LIVE crash on Kong 3.7): idempotency-key + compound-correlationId fallbacks called `kong.tools.uuid()`, which is nil on the Kong 3.x PDK global.** `handler.lua` (`generate_idempotency_key` + the MCP key) and `compound-metering.lua` (last-resort `correlationId`) fell back to `kong.tools.uuid()` — but the `kong` PDK global has no `tools` field on Kong 3.x, so any request **without an `X-Request-Id`** raised `attempt to index field 'tools' (a nil value)` in the log phase, crashing it and emitting **ZERO events** (silent total loss). Discovered live driving traffic through Kong 3.7. The unit tests were green only because BOTH spec mocks provided a fake `kong.tools.uuid` that real Kong lacks — a test-validates-a-fake trap. Fixed: both fall back to `resty.jit-uuid.generate_v4()` (bundled with OpenResty/Kong; loaded lazily + `pcall`-guarded so the modules still load under the plain-Lua unit tests) — semantically identical (a random UUID) but non-crashing. `handler.lua` VERSION 1.2.1 → 1.2.2. Regression-locked by a source-grep in both specs that fails if `kong.tools` reappears (the check the fake mock had been suppressing) plus a behavioral fallback test. Test harness hardened to run under plain Lua: stubbed the OpenResty-only load-time requires and forward-declared the self-referential `mock_kong` (a pre-existing Lua-scoping bug that made the access-phase tests unrunnable outside real OpenResty). busted 39/39.
- **Apigee: idempotency keys carried a per-execution clock.** The standard key fell back to `'apigee-' + Date.now()` and the MCP key APPENDED `Date.now()` to an already-unique `messageid + toolName` identity — any redelivery minted a fresh key, defeating ingest dedup. Keys are now computed exactly once from stable request identity (`messageid` > `x-request-id` header > one-time random fallback, never the clock) and embedded in the frozen `aforo.eventPayload` flow variable. Same freeze swept into `aforo-mcp-metering.js` (unreferenced by any bundle policy, frozen anyway). +4 unit tests (22/22) prove the exact key value, no clock component, and identical keys across re-evaluation.
- **Azure APIM: idempotency keys appended `DateTime.UtcNow.Ticks`** at both `set-body` sites — same double-billing hazard. The key base is now hoisted to a `set-variable` (`aforo-idempotency-key-base`, from `context.RequestId` — APIM's stable per-request GUID) computed once at the top of the outbound fragment; both send bodies reference the variable. The MCP key appends `toolName` (deterministic from the request body).
- **MuleSoft: the MCP idempotency key appended `now()`** to an already-unique `requestId + toolName` identity — same hazard. Now `mcp:mulesoft:{requestId}:{toolName}`, stable across attempts. Same freeze swept into `mcp-mule-policy.yaml`. The standard key (`attributes.requestId` / `correlationId`) was already stable.
- **MuleSoft: `template.xml` was not parseable XML** — shell-escape residue (`'\''` sequences from heredoc authoring) inside the `set-payload` attribute meant the file as committed could never have deployed. Replaced with `&apos;`; the file now passes xmllint end to end.

- **AWS Lambda: total send failure returned 200, permanently discarding the events.** On ingest failure the handler `console.error`'d and returned 200, which told CloudWatch Logs "success" and defeated its built-in async at-least-once retry — a recoverable ingest blip became permanent silent loss. The handler now **throws** when any batch fails after in-handler retries, so CloudWatch redelivers the identical log payload. This is dedup-safe by construction: every idempotency key derives purely from log data (`requestId || logEvent.id`; MCP: `tenant:requestId:toolName:logEventTimestamp`), so a redelivery rebuilds byte-identical keys and the ingest layer dedups — including batches that already succeeded. In-handler retry count (3) and the success path are unchanged.
- **AWS Lambda: `index.handler` was not exported.** `module.exports = { parseAccessLog, detectMcpToolCall }` (the test-export line) replaced the export object and silently dropped `exports.handler` — a deployment per `template.yaml` (`Handler: index.handler`) would have failed every invocation with "index.handler is undefined or not exported". The test exports are now additive (`exports.parseAccessLog = …`).

### Added

- **Apigee: bounded metering redelivery in PostClientFlow.** Two conditional retry `ServiceCallout` steps (`AforoMeteringSendEventRetry1/2`) + a failure-log step (`AforoMeteringLogDeliveryFailure`), each gated on the previous attempt's failure signals (`servicecallout.<policy>.failed` for transport errors and 5xx; explicit 429 status check — non-429 4xx is a permanent rejection, never retried). All three ServiceCallouts set `success.codes` to `1xx,2xx,3xx,4xx` to make that gating exact: Apigee's default success.codes (`1xx,2xx,3xx`) marks EVERY 4xx as `.failed=true`, which would have made the retry steps re-send permanently rejected events (caught in the post-ship self-review). Every attempt re-sends the SAME frozen `aforo.eventPayload` variable (byte-identical key → dedup-safe). The shared flow runs in PostClientFlow, so the client response is already sent before the primary send, let alone the retries — zero API latency added. Exhaustion sets `aforo.meteringDeliveryFailed=true` and prints to the trace session. Apigee has no wait/sleep policy, so retries are immediate sequential attempts.
- **MuleSoft: bounded redelivery around the async ingest send.** The `http:request` in `template.xml` is now wrapped in `<until-successful maxRetries="2" millisBetweenRetries="1000">` (3 total attempts, 1s backoff), inside the existing `<async>` scope — off the API response path. The payload is built once before the scope, so every attempt re-sends the identical `correlationId` key. 429 removed from the response-validator's treat-as-success range (now retryable, matching the fleet posture); exhaustion is caught by the existing `on-error-continue` and WARN-logged.

- **AWS Lambda: `EventsFailedToSend` CloudWatch custom metric** (namespace `Aforo/Metering`, emitted via Embedded Metric Format — no SDK, no extra IAM). Fires on every invocation that ends in a send failure, before the throw, so failures are alarmable while CloudWatch retries are still pending.
- **AWS Lambda: OnFailure SQS destination** (`aforo-metering-failures`, 14-day retention) + `EventInvokeConfig` (2 async retries, 6h max event age) in `template.yaml`. When CloudWatch's retries also exhaust, the failed invocation record — containing the original compressed log payload — lands in the queue instead of being discarded: the terminal loss is observable (alarm on `ApproximateNumberOfMessagesVisible > 0`) and replayable. See `aws-lambda/README.md` (new) for the replay procedure.
- **Kong: drop metric.** Buffer-overflow and flush-exhaustion drops were WARN/ERR-logged but not alarmable. `record_drop()` now maintains cumulative per-reason counters in the shared dict (`aforo_dropped:buffer_overflow` / `aforo_dropped:flush_exhausted` in `lua_shared_dict aforo_buffer`) and, when Kong's bundled prometheus plugin is loaded, increments `aforo_metering_dropped_events_total{reason}` (every prometheus touch is pcall-guarded — deployments without the plugin fall back to the dict counters + logs). The existing drop log lines are retained and now carry the cumulative total. No new config, no schema change; retry counts and the happy path untouched. Handler `VERSION` → `1.2.0`. Landed in BOTH hand-synced copies (this repo + `aforo-nextgen-docker/kong/plugins/aforo-metering/`). Spec coverage in `kong/spec/handler_spec.lua`.

### Deliberately NOT added

- **Azure APIM retry — deferred (freeze-only), documented at the send site.** `send-one-way-request` is fire-and-forget with NO observable failure signal a `<retry>` condition could gate on; an unconditional retry would duplicate-send every request; and the observable `send-request` variant waits for the ingest response inside the outbound section — which runs BEFORE the client receives the API response (APIM has no post-client-response phase), adding ingest latency (up to full timeout during an outage) to every customer request. Durable delivery for APIM is a transport change (`log-to-eventhub` + forwarder) tracked in `docs/TODO.md`. The frozen key makes that future path dedup-safe when it lands.

## v2.0.0 — 2026-04-23

**Security release** — tenant-ID IDOR fixes across 4 plugins. **BREAKING** for any deployment that was relying on `X-Customer-Id` / `X-Client-Id` / `X-Agent-Id` / `X-Tenant-Id` request headers or `?customer_id=` query params for billing attribution, rate-limit scope, or margin-guard scope.

Closes all 11 findings from the 2026-04-20 security advisory (`docs/security/2026-04-20-gateway-plugins-idor-advisory.md` in the platform monorepo).

### Severity summary

| Plugin | Severity | Findings fixed |
|---|---|---|
| MuleSoft | 2 CRITICAL + 2 HIGH | billing attribution from `X-Client-Id` header (standard + MCP), margin-guard cache-key from `x-customer-id`, preflight-quota scope-ID from `X-Customer-Id` |
| Azure APIM | 2 HIGH | margin-guard `X-Customer-Id` / `X-Tenant-Id` header reads |
| Kong | 1 HIGH + 3 MEDIUM | rate-limit `PER_CUSTOMER` reads `X-Customer-Id`, `customer_id_source: "header"` / `"query_param"` config options, cache-key poisoning in margin-guard + preflight-quota |
| Apigee | 1 MEDIUM | MCP `agentId` fallback to `X-Agent-Id` header |
| AWS Lambda | None (clean) | Documentation cleanup only — removed dead `CUSTOMER_ID_SOURCE='header'` references to prevent future re-introduction |

### What changed

**All five plugins now source tenant/customer identity EXCLUSIVELY from authenticated sources:**

1. A verified JWT claim (cryptographically validated by the plugin's JWT validation policy / filter).
2. A gateway-managed, credential-bound identity (Kong consumer, Apigee `developer.app.name`, Azure APIM `context.Subscription.Id`, API Gateway `$context.identity.apiKey`).
3. An admin-pinned configuration value (Named Value / KVM / Lambda environment variable — set by platform operators, never by end users).

**None of the five plugins will read** `X-Tenant-Id`, `X-Customer-Id`, `X-Client-Id`, `X-Agent-Id`, or `?customer_id=` from a request. Attempted spoofs are silently ignored; authenticated identity wins unconditionally.

### Upgrading from v1.x

**Before upgrading**, audit every deployment for:

1. Kong plugin configs with `customer_id_source: "header"` or `"query_param"` — change to `"consumer"` (or enable `jwt_validation_enabled`).
2. AWS Lambda deployments with `CUSTOMER_ID_SOURCE=header` environment variable — remove it.
3. Client applications that send `X-Client-Id` / `X-Customer-Id` headers for identity attribution — switch to `Authorization: Bearer <jwt>`.
4. MuleSoft API gateway configurations — apply `aforo-jwt-validation` on every API before the metering / margin-guard / quota policies. Anypoint will reject the configuration if the order is wrong.
5. Azure APIM — include `jwt-validation-policy.xml` in `<inbound>` before `margin-guard-policy-fragment.xml`.

After upgrade, verify with a forged-header smoke test:

```bash
# Request with valid JWT for customerA but spoofed X-Client-Id: customerB
curl -X GET "$GATEWAY/api/endpoint" \
  -H "Authorization: Bearer $JWT_FOR_customerA" \
  -H "X-Client-Id: customerB"
```

Expected: ingestor event attributes the usage to `customerA` (JWT-validated), not `customerB` (header spoof).
